# 04 · 技术方案与工程结构

> 本文描述**已实现**的技术方案，与 `assets/scripts` 下的代码一一对应。
> 阅读顺序建议：本文 → `docs/01-游戏设计文档-GDD.md` → 代码。

---

## 1. 技术选型

| 项 | 选择 | 理由 |
|---|---|---|
| 引擎 | Cocos Creator 3.8.x | 官方内置微信小游戏适配层，TypeScript 原生支持，2D 渲染管线轻量 |
| 语言 | TypeScript（`strict: false`） | 与引擎 API 类型一致；不开启 strict 是为了让 `!` 断言与引擎的 `getComponent` 返回类型配合更顺 |
| 场景 | 单场景 + 运行时代码构建 | 全工程只有 1 个 `.scene`，其余节点全部由代码创建，避免 Prefab 与美术资源 |
| 美术 | 零美术资源 | 所有图形用 `Graphics` 程序化绘制，所有文字用系统字体 `Label` |
| 输入 | 手动命中测试 | 不使用引擎 UI 事件系统（`Button`/`EventSystem`），改为「触摸坐标 → 自建 Rect 列表」 |
| 存档 | `sys.localStorage` | 微信小游戏由 Adapter 自动映射到 `wx.setStorageSync`，无需条件编译 |
| 动画 | 逐帧手动驱动 | 不使用 `Animation`/`Tween` 组件与帧动画资源，全部在 `update(dt)` 内推进 |

### 为什么不用美术资源

微信小游戏有硬性分包限制：**主包 / 单个分包 ≤ 4MB，总包 ≤ 8MB**。
本方案下所有 `.png`/`.plist`/字体全部为零，构建产物只有引擎代码 + 一份脚本 bundle，
首包体积只由引擎裁剪（Feature Cropping）决定，**不需要任何资源瘦身工作**。

### 分层依赖方向（单向，不允许反向）

```
Bootstrap ──► systems/GameManager ──► systems/* ──► entities/* ──► core/*
                     │                                  │
                     └────────────► ui/* ───────────────┘
                                     │
   config/* ◄── 所有层都可以直接读（只读常量，无状态）
```

- `config` 无依赖，是纯数据。
- `core` 不依赖任何业务模块。
- `entities` 只依赖 `core` 与 `config`。
- `systems` 之间允许互相持有（如 `TowerSystem` 持有 `BulletSystem` 与 `EnemySystem`），
  但**不直接调用 UI**，状态变化通过 `EventBus` 广播。
- `ui` 只读状态 + 回调，不反向调用系统内部方法（回调由 `GameManager` 注入）。

## 3. 关键技术方案

### 3.1 场景零风险：不写脚本组件，改为脚本自举

手写 `.scene` 时，若在其中挂载自定义脚本组件，必须写入该脚本的 **22 字符压缩 uuid**：

```
源 uuid   a1b2c3d4-e5f6-4a7b-8c9d-0e1f2a3b4c5d
压缩 uuid a1ssPU5fZKe4ydDh8qO0xd
```

压缩算法（引擎 `decode-uuid.ts`）：保留前 2 个十六进制字符，剩余 30 位每 3 位（12bit）编码为 2 个 base64 字符。

**风险**：一旦推导偏差，整场景反序列化失败，表现为打开场景即报错。

**方案**：`Main.scene` 退化为最普通的 `Canvas + Camera`，一个脚本组件都不挂。
`Bootstrap.ts` 在**模块顶层**注册启动钩子——Cocos 启动时会执行 `assets` 下所有脚本，
此时机早于首个场景启动，因此一定能赶上：

```ts
director.on(Director.EVENT_AFTER_SCENE_LAUNCH, () => {
    if (booted) return;
    const scene = director.getScene();
    if (scene) boot(scene);   // 找 Canvas → 应用分辨率 → 挂 GameManager
});
```

同时保留 `Bootstrap` 组件类本身：若希望显式控制启动时机，把它拖到 `Canvas` 上即可，
`booted` 标志保证不会重复启动（双保险）。

**收益**：场景文件零脚本引用，不再依赖 uuid 推导；工程可用任意 3.8.x 版本打开。

### 3.2 坐标系与布局

- 设计分辨率 **720 × 1280（竖屏）**，`ResolutionPolicy.SHOW_ALL`：设计区完整可见，多余空间留黑边。
  这一策略保证任何机型都不会裁掉顶部 HUD 或底部操作条。
- 屏幕中心为原点。`Bootstrap` 创建的 `GameRoot` 挂在 `Canvas` 的锚点上，而 `Canvas` 由引擎
  对齐到屏幕中心，因此 `GameRoot` 的局部坐标天然就是「以屏幕中心为原点」的坐标。
- 触摸坐标换算不依赖引擎内部实现，只用可见区尺寸做平移：

```ts
const ui = event.getUILocation();          // 原点在左下角
const visible = view.getVisibleSize();
const x = ui.x - visible.width / 2;        // 转成「中心为原点」
const y = ui.y - visible.height / 2;
```

布局分区（Canvas 局部坐标）：

| 区域 | y 范围 | 说明 |
|---|---|---|
| 顶部 HUD | 540 ~ 640 | 三个数据胶囊 + 暂停/倍速按钮 + 波次横幅 |
| 战场（棋盘） | -510 ~ 530 | 9 × 13 格，单格 80px，横向铺满 -360 ~ 360 |
| 底部操作条 | -640 ~ -520 | 建造卡片 / 升级出售 / 立即开始 |

### 3.3 网格与路径

- 棋盘：**9 列 × 13 行**，格边长 80px，纵向中心偏移 `PLAYFIELD_CENTER_Y = 10`。

```
cellToPos(col, row) => x = (col - 4) * 80,  y = 10 + (row - 6) * 80
posToCell(x, y)     => col = round(x / 80 + 4), row = round((y - 10) / 80 + 6)
```

- 路径由 8 个「网格坐标路点」描述（S 形折线，起止点都在棋盘外，敌人自然从屏幕外走入 / 走出）：

```
[-1,6] → [1,6] → [1,2] → [4,2] → [4,10] → [7,10] → [7,6] → [9,6]
```

- 路径格在构造时一次性算出并存入 `Set`，用于「该格能否建塔」判断。
- **移动不做寻路**：敌人只保存一个沿路径走过的像素距离 `distance`，
  `Grid.sampleByDistance(d)` 把折线按累计长度插值出坐标。

```ts
enemy.distance += speed * dt;                     // speed = 配置速度 × CELL_SIZE
const p = grid.sampleByDistance(enemy.distance);  // 折线插值
enemy.node.setPosition(p.x, p.y, 0);
```

- 索敌进度也复用同一套：`progress = distance / totalLength`，
  塔优先打 **progress 最大**（离基地最近）的敌人，行为可预期、无需空间划分。

### 3.4 手动命中测试（不使用引擎 UI 事件系统）

微信小游戏上 `Button` + `EventSystem` 需要逐节点 Raycast，节点一多成本明显；
本项目所有可点区域都是固定矩形，直接自建命中表更可控：

- 每个 UI 模块暴露 `handleTap(x, y): boolean`，返回 `true` 表示「本次点击已被我消费」。
- `GameManager` 按优先级串行分发，先命中先消费：

```
结算面板 ResultPanel  →  底部操作条 BuildMenu  →  顶部 HUD  →  棋盘 handleBoardTap
```

- 每个模块内部维护自己的 `Rect` 常量或命中表（如 `BuildMenu` 每帧按状态重建 `buttons` 数组）。
- 顶部 HUD 与底部操作条都做「整条吞掉点击」，避免误触战场。

### 3.5 主循环时序

```ts
update(dt) {
    const raw = Math.min(dt, 0.05);       // 封顶，防止切后台回来敌人瞬移穿墙
    hud.update(raw); refreshUi();
    if (over || paused) return;           // 暂停/结算时只刷 UI，不推进战斗
    const step = raw * speedMul;          // 倍速 1x / 2x / 3x
    waves.update(step);                   // ① 出怪
    enemies.update(step);                 // ② 移动 + 死亡/漏怪结算
    towers.update(step);                  // ③ 索敌 + 开火
    bullets.update(step);                 // ④ 飞行 + 命中
    fx.update(step);                      // ⑤ 特效
    checkGameOver();
}
```

顺序不可交换：先让敌人移动到位，塔再按新位置索敌，子弹最后结算命中。

### 3.6 节点层级（同层后创建的在上层）

```
Canvas
└─ GameRoot                       （屏幕中心）
   ├─ Board       静态棋盘：底色 / 格子 / 路径 / 出入口标记
   ├─ Enemies     敌人（含血条）
   ├─ Towers      防御塔 + 选中射程圈
   ├─ Bullets     子弹
   ├─ Fx          爆炸圈 / 飘字
   └─ Ui
      ├─ Hud
      ├─ BuildMenu
      └─ ResultPanel
```

**所有运行时创建的节点都强制 `layer = Layers.Enum.UI_2D`**（见 `GraphicsUtil.createUiNode`），
否则会被 Canvas 相机的 `visibility` 过滤掉、表现为「什么都不显示」。

### 3.7 对象池

敌人（80）、子弹（140）、防御塔（40）全部走 `ObjectPool`：

- 节点在构造时创建一次，之后只做 `active` 切换与 `Graphics.clear()` 重绘。
- `ObjectPool.put()` 会调用 `onRelease()` 隐藏节点；`get()` 调用 `onAcquire()`。
- `FxSystem` 内部也自带一套轻量池（爆炸圈 / 飘字各自按 `active` 复用）。

### 3.8 事件总线

`EventBus` 只做三件事：`on(event, handler, target)` / `off` / `offTarget(target)` / `emit`。

| 事件 | 触发时机 | 当前订阅方 |
|---|---|---|
| `GoldChanged` | 金币变动 | 暂无（HUD 每帧直接读） |
| `BaseHpChanged` | 基地生命变动 | 暂无 |
| `WaveStarted` | 新一波开始 | `Hud.showBanner()` |
| `PhaseChanged` | 阶段切换 | 暂无 |
| `GameOver` | 单局结束 | 暂无 |

当前 UI 采用「每帧读状态」而非「事件驱动重绘」，是为了让表现层实现简单且不会漏刷；
事件总线保留给后续需要解耦的表现（音效、成就、埋点）。
`GameManager.onDestroy` 会调 `bus.offTarget(this)` 与 `input.off(...)`，避免销毁后仍被回调。

### 3.9 数据驱动

新增塔 / 敌人 / 波次都不需要改动系统逻辑：

| 想改什么 | 改哪里 |
|---|---|
| 加一种防御塔 | `TOWER_DEFS` 加一条 + `TOWER_ORDER` 加一项（注意底部卡片宽度按 3 项布局） |
| 加一种敌人 | `EnemyConfig.ts` 的 `ENEMY_DEFS` 加一条 + `EnemyType` 联合类型 |
| 调波次组成 | `LevelConfig.ts` 的 `WAVES` 数组（`group(敌人, 数量, 间隔, 延迟)`） |
| 改难度曲线 | `GameConfig.ts` 的 `HP_GROWTH_PER_WAVE`、`START_GOLD`、`START_BASE_HP` |
| 改配色 | `GameConfig.ts` 的 `COLORS`（全部为 `0xRRGGBB`） |

## 4. 微信小游戏适配

| 关注点 | 处理方式 |
|---|---|
| 存档 | 统一走 `sys.localStorage`，Adapter 自动映射到 `wx.setStorageSync`；读写包在 `try/catch` 里，异常时回退默认值，不会崩 |
| 震动 | `Platform.vibrateShort()` 仅在 `typeof wx !== 'undefined'` 且 `wx.vibrateShort` 存在时调用，并 try/catch |
| 无 DOM/BOM | 代码中不使用 `document`/`window`；字体用 `useSystemFont = true` |
| 屏幕适配 | `SHOW_ALL`，两端留黑边；所有背景色块横向放大到 ±1000 / ±2000 覆盖黑边 |
| 首包体积 | 零资源，仅需在构建时做引擎 Feature Cropping（见 `README.md`） |

## 5. 已知取舍与后续扩展点

| 取舍 | 说明 | 扩展方向 |
|---|---|---|
| 单关卡 | 只有一条固定路径与 10 波 | 把 `PATH_WAYPOINTS` / `WAVES` 打包成 `LevelDef[]`，加选关界面 |
| 无音效 | 未接入音频 | 引入 `.mp3` 后需评估体积上限 |
| 无排行榜 | 只做本地存档 | 用微信开放数据域（`wx.getOpenDataContext`）实现好友榜 |
| 只监听触摸 | 只监听 `TOUCH_START`。引擎在桌面浏览器会把鼠标按下模拟成触摸事件，因此浏览器预览也能正常点击，无需额外适配 | 若要支持右键/滚轮再单独接入 |
| UI 每帧全量刷新 | 实现简单、不会漏刷 | `BuildMenu` 已用签名比对避免重绘；HUD 文本可同样处理 |
